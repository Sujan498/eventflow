# 17. Validation vs Business Rules

# Overview

Every request sent to a backend application must satisfy two types of checks.

1. Input Validation
2. Business Validation

Although they may seem similar, they solve completely different problems.

Understanding this distinction is essential for designing clean service layers.

---

# Two Layers of Validation

```
Client Request

↓

Input Validation

↓

Business Validation

↓

Save Data
```

The request must pass **both** layers before it reaches the database.

---

# Input Validation

Input validation checks whether the request itself is correctly formed.

It answers questions like

- Is a required field missing?
- Is a number positive?
- Is an email valid?
- Is the request format correct?

These checks do **not** require database access.

---

# Example

Consider creating a hall.

```json
{
    "venueId": null,
    "hallNumber": -1,
    "capacity": -20
}
```

Before the Service layer even executes,

Spring Validation detects the invalid request.

Result

```
400 Bad Request
```

---

# Bean Validation

EventFlow uses Jakarta Bean Validation.

Example

```java
public record CreateHallRequest(

        @NotNull
        UUID venueId,

        @Positive
        int hallNumber,

        @Positive
        int capacity

) {}
```

Spring automatically validates the request before calling the controller.

# Where Does Validation Happen?

Controller

```java
@PostMapping
public ResponseEntity<HallResponse> createHall(

        @Valid
        @RequestBody
        CreateHallRequest request

)
```

Notice

```
@Valid
```

Spring performs validation before calling

```
HallService
```

If validation fails,

the service is never executed.

# Business Validation

Business validation checks whether the request is allowed according to the application's rules.

Unlike input validation,

these checks usually require database access.

---

# Example

Request

```json
{
    "venueId":"existing-id",
    "hallNumber":1,
    "capacity":180
}
```

Everything is valid.

But...

Hall 1 already exists.

Input Validation

```
PASS
```

Business Validation

```
FAIL
```

Result

```
409 Conflict
```

---

# Business Rules in EventFlow

Hall

```
Venue must exist.

↓

Hall number must be unique.
```

Event

```
Organizer must exist.

↓

Hall must exist.

↓

Start time < End time.

↓

Hall must not already be booked.
```

These rules cannot be checked using annotations.

They require database queries.

---

# Example

Inside HallService

```java
Venue venue = venueRepository
        .findById(request.venueId())
        .orElseThrow(
                () -> new VenueNotFoundException(
                        "Venue not found"
                )
        );
```

Question

```
Does this Venue exist?
```

Only the database can answer this.

---

Another example

```java
boolean exists =
        hallRepository.existsByVenueIdAndHallNumber(
                request.venueId(),
                request.hallNumber()
        );
```

Question

```
Does Hall 1 already exist?
```

Again,

requires the database.

---

Event creation

```java
boolean conflicting =
        eventRepository.existsConflictingEvent(
                hall.getId(),
                request.startTime(),
                request.endTime()
        );
```

Question

```
Is another event already using this hall?
```

Only the database knows.

---

# Validation vs Business Rules

| Input Validation | Business Validation |
|-----------------|---------------------|
| Checks request format | Checks business logic |
| No database needed | Database usually required |
| Uses annotations | Uses Service layer |
| Returns 400 | Usually returns 404 or 409 |

---

# Why Separate Them?

Suppose every request reached the database.

Even

```json
{
    "capacity":-5
}
```

would execute SQL.

Waste of resources.

Instead,

Spring rejects invalid requests immediately.

Only valid requests reach the business logic.

This improves

- Performance
- Readability
- Separation of concerns

---

DTO

Each layer has a single responsibility.

# EventFlow Request Lifecycle

```
HTTP Request

↓

DTO Validation

↓

Controller

↓

Service

↓

Business Validation

↓

↓

Database

↓

Response
```

Notice

Validation happens twice,

but for different reasons.

---

# Common Beginner Mistakes

❌ Checking duplicate hall using annotations.

Impossible.

Requires database access.

---

❌ Putting business rules inside repositories.

Repositories should retrieve data,

not make business decisions.

---

❌ Returning database exceptions to users.

Instead,

throw meaningful custom exceptions.

Example

```
DuplicateHallException

HallAlreadyBookedException

VenueNotFoundException
```

---

# Best Practices Used in EventFlow

✔ Use Bean Validation for request correctness.

✔ Use Service layer for business decisions.

✔ Use repositories only for database access.

✔ Throw custom exceptions.

✔ Return meaningful HTTP status codes.

---

# Summary

EventFlow separates request validation into two independent stages.

```
DTO Validation

↓

Business Validation

↓

Persistence
```

Input validation ensures the request is correctly formed.

Business validation ensures the request follows the application's rules.

Keeping these concerns separate results in cleaner code, better performance, and a service layer that is easier to maintain as the application grows.
